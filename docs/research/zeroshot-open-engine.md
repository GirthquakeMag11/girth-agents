# How zeroshot (the-open-engine) spawns and connects agent sessions — and what transfers to a build-verify-rectify loop of fresh OpenCode sessions

**Question:** How does the `zeroshot` project by the-open-engine work mechanically — specifically its approach to spawning fresh OpenCode sessions/agents and passing information between them — and what transfers to a system that spawns fresh OpenCode sessions for a build-verify-rectify loop?

**Date:** 2026-10-25

**Project investigated:** `the-open-engine/zeroshot` (MIT license), `https://github.com/the-open-engine/zeroshot`. The the-open-engine organization has exactly two public repos (`zeroshot`, `opcore`), and this is the only repo matching "zeroshot", so identification confidence is high. Findings below are pinned to two revisions of the primary source (the repo itself):

- **Current main (v8+ era, "native" Rust engine)**: commit `eb899ad4302e7929b60859b074fbc931a27a6a41` (2026-10-25). Cited below as `main@eb899ad`.
- **Last revision containing the OpenCode provider adapter** (v5–v7 era, TypeScript engine): commit `7bb019a9b1877d921e57a69a28d1ee1d8f016bc8` (2026-09-06, the parent of the v8 cutover commit `a40bd9a5b5727a86dc2329c9b79384bf2a9a40ac` "feat!: make Rust Zeroshot canonical in v8 (#1074)", dated 2026-09-07, which deleted every OpenCode file). ## 1. What zeroshot is for, and its core loop

- Current headline: "Prompts are suggestions. Graphs are enforced." — a caller-authored workflow graph of implementation, review, repair, and delivery steps; "its authored transitions decide which node runs next, so no agent skips a step." — `docs/index.md` @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/docs/index.md).
- The built-in `software-change` loop: (1) worker implements; (2) acceptance + code reviewers check independently, in parallel; (3) rejected work returns to the same worker with both reviews' feedback, then through both reviews again; (4) optional delivery; (5) delivery conflicts return through repair and review. — `README.md` lines 239–251 @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/README.md).
- The v7-era README states the invariant in one sentence: "Validators do not share the executor's session or reasoning context; they may receive explicit handoff artifacts and must reproduce reported failures." — `README.md` ("How it works") @ `v7@7bb019a9` (https://github.com/the-open-engine/zeroshot/blob/7bb019a9b1877d921e57a69a28d1ee1d8f016bc8/README.md).
- Same v7 README: a *conductor* classifies every task (complexity TRIVIAL/SIMPLE/STANDARD/CRITICAL, type INQUIRY/TASK/DEBUG) and that score picks the workflow (0–4 validators); every step is written to a crash-safe SQLite ledger; zeroshot "orchestrates their CLIs without storing provider keys." — `README.md` @ `v7@7bb019a9` (same URL).
- Self-description in GitHub metadata at the time of cloning: "Open-source meta-harness for coding agents. Define your own workflows, reviewers and repair loops. zeroshot enforces the process you configure." — https://api.github.com/repos/the-open-engine/zeroshot (fetched 2026-10-25).

## 2. Architecture eras (what changed)

- Pre-v8: Node/TypeScript engine (`src/`), a message-bus cluster of agents wired by JSON workflow templates (`cluster-templates/base-templates/`), one adapter per provider CLI including `opencode`. — repo tree @ `v7@7bb019a9` (https://github.com/the-open-engine/zeroshot/tree/7bb019a9b1877d921e57a69a28d1ee1d8f016bc8).
- v8+: Rust engine (`zeroshot/` crate) with native turn-based drivers for `codex`, `claude`, `copilot`, `pi` only; graph/runtime-plan protocol in `crates/openengine-cluster-*`. OpenCode was dropped, not reimplemented. — tree @ `main@eb899ad`; deletion commit `a40bd9a5b5727a86dc2329c9b79384bf2a9a40ac` (https://github.com/the-open-engine/zeroshot/commit/a40bd9a5b5727a86dc2329c9b79384bf2a9a40ac).
- The two eras share the same concepts (sessions scoped per node, typed verifier signals, ledger), so both are cited below.

## 3. How zeroshot spawns agent sessions (the OpenCode path, v5–v7)

The provider abstraction was "CLI-backed": zeroshot shelled out to an installed agent CLI per node execution, rather than using an SDK or a client library.

- The OpenCode adapter drives the `opencode` CLI binary with: `opencode run [--format json] [--agent NAME] [--model ID] [--variant EFFORT] [--dir DIR | --cwd DIR] [--session ID | --continue] <context>`, where `<context>` is the node prompt passed as the final positional argument. — `src/agent-cli-provider/adapters/opencode.ts`, functions `addOpencodeOptionalArgs`, `addSessionArgs`, `buildCommand` @ `v7@7bb019a9` (https://github.com/the-open-engine/zeroshot/blob/7bb019a9b1877d921e57a69a28d1ee1d8f016bc8/src/agent-cli-provider/adapters/opencode.ts).
- It does **capability probing**: it parses `opencode` help/version text for `--format`, `--model`, `--variant`, `--dir`, `--cwd`, `--session`/`--continue`, `--agent`, and adapts the command to what the installed CLI actually supports; version parsing gates web search (≥ 1.0.137) and output-recovery isolation (≥ 1.17.20). — same file, `detectCliFeatures` (lines 41–61).
- **Fresh session by default**: with no resume flags the adapter emits a plain `opencode run <context>`; the CLI process itself is the session, and it ends when the process exits. Continuation is opt-in. — same file, `addSessionArgs` (lines 105–131).
- **Reuse by explicit session ID**: to continue the same node's session across a loop iteration, zeroshot captures the session ID from the JSONL event stream (`sessionID` / `sessionId` fields via `extractSessionId`, lines 145–150) and later passes `--session <ID>`; a bare continue passes `--continue`. — same file, lines 126–130; session-reuse across agents landed in commit `0dab9f05da6aa49827ec957f79c0c972d06b668c` "feat: reuse provider sessions per agent (#811)" (https://github.com/the-open-engine/zeroshot/commit/0dab9f05da6aa49827ec957f79c0c972d06b668c).
- **Working directory**: the adapter passes `--dir` (fallback `--cwd`) so the agent runs in the isolated worktree, not the main repo — commit `b132ffdcf67a0c4eb688762f65a738c1d7aef89e` "fix(opencode): pass --dir to opencode so agents run in the worktree, not main repo (#816)" (https://github.com/the-open-engine/zeroshot/commit/b132ffdcf67a0c4eb688762f65a738c1d7aef89e).
- **Output ingestion**: it runs the CLI with `--format json` and parses the JSONL events it recognizes: `text` parts as text, `reasoning` as thinking, `tool` parts by `state.status` (`pending`/`running` → tool_call, `completed`/`error` → tool_result), and `step-finish` parts carrying `tokens.input`/`tokens.output` as the result with token counts; `error` events become failed results. — same file, `parsePart`/`parseEvent` (lines 247–341).
- **Forced structured-output recovery**: when a node's typed output was malformed, zeroshot re-invoked OpenCode *in a second, fully isolated session* with a generated ephemeral agent (`zeroshot-output-reformatter-<uuid>`, permissions `{"*":"deny"}`, all tools disabled), a fresh temp `XDG_CONFIG_HOME`, inline config via `OPENCODE_CONFIG_CONTENT`, `OPENCODE_DB=:memory:`, `OPENCODE_PERMISSION={"*":"deny"}`, and disable switches for project config, plugins, external skills, and CLAUDE.md — i.e. a zero-context reformat-only subprocess, not a resume of the original session. — same file, `buildStructuredOutputRecoveryCommand` (lines 171–245); introduced by commit `17028d9b99053413c8c963c1c348356f12edf2bc` "fix(opencode): implement reformatOutput so structured-output agents recover (#803)" (https://github.com/the-open-engine/zeroshot/commit/17028d9b99053413c8c963c1c348356f12edf2bc).
- Credentials: the adapter declares `OPENCODE_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY` as the credential env keys it may forward — `opencode.ts` lines 352–358 (same URL).
- Web search, opt-in: `providerSettings.opencode.webSearch: true` adds env `OPENCODE_ENABLE_EXA=1` to both fresh and resumed `opencode run` commands, and fails closed before starting the provider if the installed OpenCode CLI can't be proven ≥ 1.0.137. — `docs/providers.md` @ `v7@7bb019a9` (https://github.com/the-open-engine/zeroshot/blob/7bb019a9b1877d921e57a69a28d1ee1d8f016bc8/docs/providers.md).
- The same docs table lists OpenCode as a first-class provider ("Opencode | Opencode | See https://opencode.ai") alongside Claude Code, Codex, Gemini, Pi — `docs/providers.md` @ `v7@7bb019a9`.
- Model selection: external/configured model IDs allowed via commit `088db993ed2a1c479c2df797951f3bfe81a01a6d` "feat(opencode): allow configured external models (#807)" (https://github.com/the-open-engine/zeroshot/commit/088db993ed2a1c479c2df797951f3bfe81a01a6d); resolved through a bounded model catalog plus per-provider level mapping in `src/agent-cli-provider/adapters/opencode-models.ts` @ `v7@7bb019a9`.

## 4. How the current (v8+) engine spawns and terminates sessions

Even without OpenCode, the current Rust engine's per-node session mechanics are the transferable template:

- Each executable node gets an `agent` binding with `harness`, `provider`, `model`, `effort`, and **`sessionScope`**: `execution` (default) = "Opens a fresh provider session for each execution of the node, then closes it"; `node_instance` = "Reuses one session when the same node instance runs again, for example across loop iterations." If a reused session is lost, that execution fails with `session_lost` — no silent replacement session. — `docs/reference/runtime-plan.md` lines 111–118 @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/docs/reference/runtime-plan.md).
- **Template defaults encode the review pattern**: for `software-change`, an omitted `sessionScope` defaults to `node_instance` for `worker` and `execution` for both reviewers — "The worker retains its session through implementation and every repair; reviewers start fresh each pass." For `auto-research`, explorer/synthesizer/challenger/researcher default to `node_instance`, reviewer to `execution`. — `runtime-plan.md` lines 320–331 @ `main@eb899ad` (same URL); same split stated in `README.md` lines 218–221.
- One harness adapter is started per distinct harness/provider "lane"; each node runs on its own lane's CLI; the CLI executable must be on `PATH` before the controller starts (checked for `codex`/`claude`/`copilot`/`pi`). — `docs/concepts/runtimes-and-connections.md` lines 14–27; `runtime-plan.md` lines 236–252 @ `main@eb899ad`.
- The native drivers spawn **one CLI process per turn** (not a long-lived daemon session): the Claude driver builds argv per turn including `--resume <session-id>` only when continuing, passes the prompt on stdin, writes the whole environment fresh per turn, moves HOME/TMPDIR into a provider-private per-session home, and derives a workspace capability (read-write for workers *and* verifiers) from the node role. — `zeroshot/src/native_v2_claude.rs` @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/zeroshot/src/native_v2_claude.rs) functions `command`, `process_environment`, `advance_turn`, `execute_turn`.
- There is a recurring "Continue" turn in the same opened session (const `CONTINUE_PROMPT`, and correction turns described in §6) — `zeroshot/src/native_v2_capsule/provider_process.rs` line 72 @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/zeroshot/src/native_v2_capsule/provider_process.rs).
- **Verifiers run read-write on the same live workspace**; the no-edit rule is a prompt instruction, not a filesystem boundary: "Agent roles share execution permissions; verifier edit restrictions live in the prompt." — `provider_process.rs` lines 74–82; `docs/concepts/targets.md` lines 101–111 ("the restriction on edits is instruction guidance, not a filesystem boundary") @ `main@eb899ad`.
- **Termination** is explicit and layered: every node has a declared `timeoutMs` (built-in templates use 60 min) and `attempts` (`attempts: 1` on workers/verifiers — `native_v2_templates.rs` @ `main@eb899ad`); runs admit a `stop {mode: drain|force}` where force signals every lease's cancellation token and records each cancelled turn as structural void; the final `finished` ledger record is atomic and rejects any later event. — `docs/reference/cluster/lifecycle.md` ("Stop") @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/docs/reference/cluster/lifecycle.md); "When a run closes, Zeroshot atomically closes its execution activity; a late process cannot appear after the terminal result." — `docs/concepts/execution.md` lines 67–75.
- Isolation boundary for untrusted runs is the "disposable capsule" (Docker container), not per-session sandboxing: hosted Codex/Claude turns run with full bypass flags "inside the disposable capsule"; hosted nodes share the prepared workspace and owner identity but retain separate session homes and process-cleanup markers "so ending one node does not terminate another node or the run's startup services." — `docs/concepts/targets.md` lines 88–111 @ `main@eb899ad`; capsule data-plane surface defined at `docs/reference/cluster/data-plane.md` lines 60–64.

## 5. How information passes between sessions

This is the part most directly analogous to "records passed between fresh sessions":

- **Typed state, not transcripts.** Between-node data flows as authored, schema-checked state: a verifier returns `{output, signals, diagnostic}`; `writeBindings` copy the diagnostic into named state fields (e.g. `acceptanceFeedback`, `codeFeedback`); the next run of the worker reads those fields via `inputBindings`. "The worker uses `node_instance`... The reviewers use `execution`, so each review starts a fresh session and does not see the previous pass. The graph state still carries the feedback explicitly either way." — `docs/guides/review-loop.md` lines 88–112, 183–185 @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/docs/guides/review-loop.md).
- **The prompt a node receives is assembled from three things only**: authored instructions (per node), the node's current typed input (task + whatever feedback fields the graph routed to it), and the machine-generated response contract (a closed JSON schema for `response` or `response`+`signals`+`diagnostic`). It is built by `render_agent_prompt` in Rust: "Execute this graph node using the shared workspace. Authored instructions: … Input JSON: … Runtime-owned response contract: …". Nothing from another node's conversation enters this prompt unless the graph explicitly bound it into state. — `zeroshot/src/native_v2_runner/response.rs`, `render_agent_prompt` (lines 446–466) @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/zeroshot/src/native_v2_runner/response.rs).
- **v5-era message-bus form of the same idea**: each agent declared a `contextStrategy` — which message topics it pulls into its context, with `strategy: "latest"`, `amount: N`, `since: last_task_end`, a chronological format, and a `maxTokens` budget. The validator's context = `ISSUE_OPENED` + `STATE_SNAPSHOT` + `IMPLEMENTATION_READY` (the worker's typed summary) — deliberately *not* the worker's transcript; the worker's post-rejection context = `VALIDATION_RESULT` (a typed `{approved:false, errors:[…]}` message) + issue + snapshot. — `cluster-templates/base-templates/worker-validator.json` @ `v7@7bb019a9` (https://github.com/the-open-engine/zeroshot/blob/7bb019a9b1877d921e57a69a28d1ee1d8f016bc8/cluster-templates/base-templates/worker-validator.json).
- **Handoff artifacts + reproduction**: the verifier is told it may receive "explicit handoff artifacts" and "must reproduce reported failures" — the check is against the observable workspace, not against the executor's claims. — `README.md` ("How it works") @ `v7@7bb019a9`; v7 validator prompt enforces a verify-by-search/read/grep protocol ("NEVER claim something doesn't exist without FIRST searching for it") — `cluster-templates/base-templates/worker-validator.json` @ `v7@7bb019a9` (same URL).
- **Shared workspace is the bulk channel**: state passes through the filesystem. `par` branches and reviewers explicitly share the run's workspace, and the docs warn that "the graph and agent instructions must coordinate edits to the same files" — `docs/concepts/execution.md` lines 45–55 @ `main@eb899ad`. In v7-era local mode the workspace was a git worktree; hosted/Docker mode clones an exact commit into a container. — `README.md` @ `v7@7bb019a9` ("guided default runs in a separate worktree"); `docs/concepts/targets.md` lines 174–184 @ `main@eb899ad` (targets receive "the remote revision", Docker/hosted require a Git source with an exact committed revision).
- **File-based records for the research loop**: `auto-research` keeps "the charter, current summary, backlog, round evidence, and restorable candidate source" under `.zeroshot/research` at the workspace root; the reviewer each round is a fresh session that reads those records; corrections return to the same researcher session. — `docs/concepts/execution.md` lines 101–131 @ `main@eb899ad`.
- **Cross-run memory (Active Memory)**: after the main graph settles, a postmortem maintains a lessons store (`lessons.sqlite3`, local default `~/.local/state/zeroshot/active-memory/`); matching is deterministic by file/folder/identifier/keywords with scores (exact file 1000, folder 800, identifier 700, keyword group 500); at most `budgetBytes` (default 2048) of cards are injected per provider session; repository cards are injected through harness hooks (Codex/Claude `PreToolUse` additional context), graph cards into node instructions after admission. Workers never write lessons. — `docs/guides/active-memory.md` @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/docs/guides/active-memory.md).
- **Durable run ledger + checkpoints**: every node outcome, cursor, and lifecycle event goes to a per-run SQLite ledger with opaque cursors enabling strict resume after detach/lost terminal/cancelled await — `docs/concepts/execution.md` lines 67–75; SQLite storage implemented in `zeroshot/src/v2_run_ledger/sqlite.rs` @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/zeroshot/src/v2_run_ledger/sqlite.rs). Per-node workspace snapshots (input checkpoints) are restorable: `zeroshot checkpoints RUN_ID`, `zeroshot resume RUN_ID --from-checkpoint ID`; "A selected checkpoint restores the files from immediately before its node and the completed prerequisite outputs"; checkpoints are deduplicated in a private Restic repository beside run storage. — `docs/guides/observe-and-control.md` lines 75–109 @ `main@eb899ad` (https://github.com/the-open-engine/zeroshot/blob/eb899ad4302e7929b60859b074fbc931a27a6a41/docs/guides/observe-and-control.md).

## 6. Verification / grading and rectification

- **Typed verdicts**: verifier nodes declare finite-enum signals — the built-in reviewers emit `verdict: "accepted" | "rejected"` plus a diagnostic message; graph guards (not the model) route: `par`-join of the two reviewers, then a `choice` on `all accepted` → succeed, otherwise back to repair; the loop is do-while with `maxIterations` (4 in the walk-through, 10 in the built-in change loop; `auto-research` review/repair has a 64-pass safety limit). — `docs/guides/review-loop.md` lines 88–160; `zeroshot/src/native_v2_templates.rs` (`CHANGE_ITERATIONS = 10`, `review_verifier`, `signal_guard`) @ `main@eb899ad`; `docs/concepts/execution.md` lines 101–114.
- The graph *enforces* the verdict consequences: "Inside a repair loop, a reviewer emits a finite signal with a typed diagnostic. The graph routes that signal to success or another iteration, and `maxIterations` still applies if an agent asks to continue." Model output cannot add an edge or raise a bound. — `docs/concepts/execution.md` lines 57–65 @ `main@eb899ad`.
- v5-era verdict was an `approved: boolean` in the validator's JSON schema, published as a `VALIDATION_RESULT` topic message; the worker's rejection-trigger re-reads the ledger (`approved === false`), and the worker's re-invocation prompt includes a "SUBSEQUENT ITERATIONS (after rejection)" block. — `cluster-templates/base-templates/worker-validator.json` @ `v7@7bb019a9`.
- **Malformed outputs are not passed to the graph**: mechanical validation rejects bad responses, and up to two correction turns re-run *in the already-open session* with the error text and contract; "Your previous final response was rejected mechanically and was not passed to the graph." — `zeroshot/src/native_v2_runner/response.rs`, `render_agent_correction` and `MAX_OUTPUT_CORRECTIONS = 2` (same file, lines 468–481 and top). The OpenCode-era equivalent was the isolated reformatter subprocess (§3).
- Reviewer instructions are authored per node and are the only "review policy": e.g. acceptance verifier "Verify the change independently against the user's request and observable behavior. Do not edit files… Accept only with concrete evidence; otherwise return actionable feedback." — `zeroshot/src/native_v2_templates.rs` lines 144–169 @ `main@eb899ad`; plus automatically added inspection-only guidance for every verifier — `docs/concepts/targets.md` lines 101–106.
- **Delivery as a verifier**: Git delivery is a trusted non-agent `verifier` node with its own fixed contract, one per run, after all other work; reviewer/worker disagreements about CI or merge conflicts route back as `deliveryFeedback` through repair *and* both reviews again. — `docs/reference/runtime-plan.md` lines 121–162; `README.md` lines 239–251 @ `main@eb899ad`.

## 7. Agent architecture: fresh contexts, budgets, idempotency, caps

- **Freshness is the default, reuse is the exception**: every verification opens a fresh provider session (per execution); only the author side reuses sessions, and only per node instance. — `runtime-plan.md` lines 111–118; the review-loop guide's rationale: a fresh reviewer session "does not see the previous pass", preventing self-confirming loops. — `review-loop.md` lines 183–185 @ `main@eb899ad`.
- **Budgeting**: per-node wallet = `timeoutMs` + `attempts`; loops/maps are bounded (`maxIterations`, `maxItems`) with a single pass over all bounds; aggregate bound violations produce `ceiling_exceeded`; admission requires bounds — "bounds are checked over the bounded legal control space", and "The graph defines … retry paths, and exit conditions before execution starts. Runs are bounded." — `docs/reference/cluster/graph.md` (lines 140–209) and `README.md` line 249 @ `main@eb899ad`; the v5-era contexts also had literal `maxTokens` context budgets — `worker-validator.json` @ `v7@7bb019a9`.
- **Idempotency and crash-safety**: admission is validate-then-run (`--validate-only`); runs are the atomic unit ("Reusing a submission key for another folder returns a conflict"); lifecycle mutations carry idempotency keys and a generation CAS; `retry` is the single authoritative same-run retry that reuses "the exact recorded verified input, admitted target, workspace policy, and deadline… it never accepts caller-supplied replacement data"; `resubmit` mints a new run from a terminal run. — `docs/concepts/targets.md` lines 22–26; `docs/reference/cluster/lifecycle.md` ("Retry", "Resubmit") @ `main@eb899ad`.
- **Ledger survives reboot**: local runs detach a controller and keep the ledger under the local state directory, "where later CLI invocations can list, watch, or stop the run"; runs can be restarted or resumed after failure. — `docs/concepts/targets.md` lines 17–35; `README.md` lines 150–159 @ `main@eb899ad`.
- **Zero-context subprocesses are load-bearing**: the malformed-output reformatter is the cleanest example of spawning a brand-new, fully neutered agent (deny-all permissions/tools, no project config, no CLAUDE.md, in-memory DB) to do one mechanical job with only the text supplied on stdin — `opencode.ts` lines 171–245 @ `v7@7bb019a9`.

## Transferable / Not transferable (for a records-first build-verify-rectify engine on OpenCode)

Caveat that frames everything: zeroshot is a **workspace-first orchestrator**; it makes claims about *the checked-out files*, not about a records artifact a caller wrote. Its graphs and runtime files are deliberately kept **outside** the folder being changed ("keep them outside the folder you are changing… so they stay out of the change" — `review-loop.md` lines 24–29). A records-first design (plans/specs/tickets in the project repo as source of truth) inverts this: the records *are* the artifact under review.

**Transferable, near verbatim**

- **`sessionScope: execution` as the review default** — spawn a fresh OpenCode session per verification pass, reuse (by explicit session ID) only for the builder across rectification passes, and fail loudly (`session_lost`, no silent fallback) if the reused session is gone. This is zeroshot's single most portable idea (`runtime-plan.md` lines 111–118).
- **The exact OpenCode invocation pattern** has aged well: every flag the adapter used — `opencode run <context>`, `--format json`, `--model`, `--agent`, `--variant`, `--dir`, `--session`, `--continue` (and now `--fork`) — still exists in the current OpenCode CLI, along with the isolation env vars (`OPENCODE_CONFIG_CONTENT`, `OPENCODE_CONFIG_DIR`, `OPENCODE_PERMISSION`, `OPENCODE_DB=:memory:`, `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_DISABLE_EXTERNAL_SKILLS`, `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_DEFAULT_PLUGINS`, `OPENCODE_PURE`, `OPENCODE_ENABLE_EXA`). — https://opencode.ai/docs/cli/ (CLI reference, updated 2026-10-24). A regenerated approach: probe `--help` for flags like zeroshot did, don't assume.
- **Capability probing + version gating** over the CLI, and failing closed before starting a stage when a needed capability is missing (zeroshot's `detectCliFeatures`).
- **Typed verdict signals checked by the harness, never by free text**: a reviewer whose only channel out is `{verdict ∈ {accepted, rejected}, diagnostic}` with a JSON-schema contract; routing into repair as a do-while with `maxIterations`, plus a structural safety cap (zeroshot's 64-pass limit for auto-research). A records-first engine can grade PASS/FAIL identically, with the *review report* as the diagnostic record.
- **writeBindings/inputBindings as the hand-off protocol**: pass only (a) the task record, (b) the accumulated feedback records, and (c) authored stage instructions into each fresh session — never the previous session's transcript. The v5-era `contextStrategy` (topic → latest N messages → maxTokens budget → chronological format) is a concrete template for building a stage "brief" from stored records.
- **Mechanical output discipline when agents write files**: parse the fresh session's JSON output, mechanically reject malformed values, and retry with a correction turn in the same session (zeroshot allows 2; the OpenCode-era reformatter shows the emergency escalation: an isolated, tool-less, config-less subprocess that only reformats). Exactly right for grading PASS/FAIL reports off agent-written JSON records.
- **Durable ledger + typed events with opaque cursors for resume; per-stage checkpoint records** so a crashed pipeline resumes exactly where it stopped (SQLite ledger; Restic snapshots are overkill for records-only stages — records files are the cheaper equivalent).
- **Idempotency in the protocol**, not good behavior: submission keys, generation CAS, single retry point that consumes the recorded frontier. For a records-first engine: a stage run must be repeatable off its input records; retry must re-read the record, not ask the agent.
- The v7-era "conductor classification" (size the pipeline from the record before running it) — cheap to replicate: derive pipeline depth from tags on the ticket/spec.

**Transferable with adaptation**

- **Verifier "fresh sessions, same live workspace"**: zeroshot reviewers re-inspect the worktree itself. In a records-first engine the analog is: reviewer sessions run against the *repo*, but graded evidence is the records (plans/spec diffs, build logs), and the reviewer's own report becomes the next record. Note zeroshot's no-edit enforcement is prompt-only; if you want records immutability, that is a real boundary (write protection on the records tree, or the records path passed as read-only input) — zeroshot itself shows the pragmatic fallback that instructions are enough when all agents are trusted.
- **Active Memory**: the store/retention mechanics (host-owned SQLite store outside checkouts; deterministic file/identifier/keyword retrieval; bounded injection budget per session; workers never write lessons) map directly onto a "lessons/decisions" record family in the project repo. Its hook-based injection (PreToolUse for Codex/Claude) maps onto OpenCode skills/instructions rather than env vars; its conservatism (two rejected rounds or two crashes qualify; no findings-quota) is worth copying.
- **The graph contract itself** (seq/choice/par/loop/map groups, signals, writeBindings, admission validation, terminal succeed/fail with reasons) as the *shape* of a pipeline definition — but see below: for you the pipeline likely lives as a record file in the repo, not as caller-owned JSON outside it.

**Not transferable / actively in tension with a records-first + user-TUI design**

- **OpenCode support is gone from zeroshot proper.** Its OpenCode adapter is historical (deleted 2026-09-07, commit `a40bd9a5…`); the maintained harnesses are Codex/Claude/Copilot/Pi, targeting those CLIs' specific flags (`--resume`, `--dangerously-*`, etc.). Anything you borrow for OpenCode must be re-verified against the OpenCode CLI you actually pin, because zeroshot will not track it for you.
- **Single-writer, live-workspace assumption**: zeroshot grants every agent (including reviewers) concurrent read-write access to the same workspace and coordinates edit conflicts with prompt text ("Writers share the run's workspace… so the graph and agent instructions must coordinate edits to the same files" — `execution.md` lines 45–55). A records-first engine where user-driven OpenCode TUI sessions are editing the repo **in parallel** violates this worst: zeroshot-style checkpoint restores ("selecting a checkpoint replaces later workspace edits, including untracked and ignored files" — `observe-and-control.md` line 101) would clobber user work, and local mode's workspace/state-dir disjointness rule is a non-starter if your records live inside the workspace.
- **Workspace-level verification is the wrong grain for records**: zeroshot's verifiers grade "the observable result" (running the stack, reproducing failures), and only incidentally read authored state. A records-first loop needs the reverse emphasis — grade the record (does the plan cover the spec? the build report match the diff? the rectify ticket address the review?) with the workspace as supporting evidence. The hand-off brief (task + only explicitly bound feedback) is the right pattern; "verifier reads the whole repo fresh" is not a substitute for "verifier reads the records".
- **Config outside the repo is backwards for you**: zeroshot explicitly keeps graph/runtime/input files out of the changed folder and profiles in a config store (`ZEROSHOT_CONFIG_DIR`), with stable submission input; keep your pipeline definition and stage records *inside* the repo (they are the thing being tracked), or nothing like git blame, PR review of the pipeline, or user-TUI visibility of stage records works.
- **No concept of a concurrent human session**: everything zeroshot does assumes it owns the checkout (worktree, container, or the caller's folder, which local mode is allowed to mutate). There is no notion of another OpenCode session editing the same repo. Anything you design with "each pipeline stage = a fresh OpenCode session, user works in the same repo in parallel" must add zeroshot's missing layer: a *write discipline* (e.g. stages only write under their record paths and a stage-owned worktree/branch; users own the rest), which zeroshot simply has no machinery for.
- **Secrets and heavy containers**: zeroshot's capsule/UID-isolation and Restic checkpoint machinery are about untrusted hosted runs; for a local, records-first loop they are pure overhead. Borrow the philosophy (disposable per-stage environment, `OPENCODE_DB=:memory:`-style hygiene) not the infrastructure.

**The single strongest takeaway** is the discipline zeroshot enforces between sessions: what a fresh session may know is *exactly* (authored instructions) + (explicitly bound typed records) + (own typed output contract) — and the state machine, not the model, decides what happens next. A records-first build→verify→rectify engine can copy that rule wholesale: each fresh OpenCode session = one stage, its brief compiled from records in the repo, its verdict written back as the next record, and PASS/FAIL decided by validating the record, not by asking the agent whether it succeeded.
