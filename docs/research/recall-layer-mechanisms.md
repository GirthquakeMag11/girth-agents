# Recall-layer mechanisms in real agentic systems

**Question this feeds:** We are designing an "engine" (an OpenCode plugin) whose helper agents do repeated work across sessions in a project. We want a recall layer so a lesson the system learns is learned ONCE — capture a lesson when it happens, recall it later to avoid re-learning — reconciled with our existing canonical, committed "hazards" tracker.

**Research date:** 2026-10-26

Every claim below carries a citation: an exact documentation URL with section anchor, or a repo path + commit SHA. No blog summaries or marketing content were used.

---

## 1. Claude Code — auto memory vs CLAUDE.md

First-party doc: <https://code.claude.com/docs/en/memory>

- **Two mechanisms, both loaded at session start.** "Each Claude Code session begins with a fresh context window. Two mechanisms carry knowledge across sessions: CLAUDE.md files (instructions you write) and auto memory (notes Claude writes itself based on your corrections and preferences)." (`#how-claude-remembers-your-project`)
- **Human-authored vs auto.** CLAUDE.md is "Who writes it: You … Instructions and rules"; auto memory is "Who writes it: Claude … Learnings and patterns." CLAUDE.md is scoped "Project, user, or org"; auto memory is "Per repository, shared across worktrees." Both are "Loaded into: every session". (`#claude-md-vs-auto-memory` table)
- **Loaded budget differs.** CLAUDE.md loads whole at session start; auto memory loads "first 200 lines or 25KB" at session start. (`#claude-md-vs-auto-memory`, "Loaded into" row)
- **Neither is enforced.** "Claude treats them as context, not enforced configuration"; CLAUDE.md "content is delivered as a user message after the system prompt, not as part of the system prompt itself … there's no guarantee of strict compliance." (`#claude-md-vs-auto-memory`, `#claude-isnt-following-my-claude-md`)
- **The four memory KINDS.** "Claude saves four kinds of notes for itself. Claude records the kind as a `type` field in the memory file's frontmatter: `user` (role, expertise, working preferences); `feedback` (corrections you give Claude and approaches you confirm); `project` (ongoing work, deadlines, decisions Claude can't derive from code or git history); `reference` (where to find information outside the project)." (`#auto-memory`)
- **Capture trigger is self-decided, not idle-gated.** "Claude doesn't save something every session. It decides what's worth remembering based on whether the information would be useful in a future conversation." (`#auto-memory`)
- **De-duplication / "already learned" behavior.** "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." (`#auto-memory`)
- **Storage — git-repo keying.** "Each project gets its own memory directory at `~/.claude/projects/<project>/memory/`. The `<project>` path is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory. Outside a git repo, the project root is used instead." Machine-local only. (`#storage-location`)
- **Layout — index + topic files.** The directory holds "a `MEMORY.md` index and one topic file per memory"; "`MEMORY.md` acts as an index … Claude reads and writes files in this directory throughout your session, using `MEMORY.md` to keep track of what's stored where." (`#storage-location`)
- **Budget enforcement.** "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation. Content beyond that threshold is not loaded at session start. Claude keeps `MEMORY.md` concise by moving detailed notes into separate topic files." If `MEMORY.md` is over a limit "the write still succeeds, but Claude Code returns an error telling Claude to rewrite the index, because everything past the limit is dropped on the next load." (`#how-it-works`)
- **Retrieval is on-demand for topic files.** "Claude Code doesn't load topic files such as `user_role.md` … at startup. Claude reads them on demand using its standard file tools when it needs the information." During a session the UI shows "Saved 2 memories" / "Recalled 2 memories". (`#how-it-works`)
- **Freshness metadata.** "When Claude writes a memory file that begins with YAML frontmatter, Claude Code records the write time in a `modified` frontmatter field as an ISO 8601 timestamp." (`#how-it-works`)
- **Subagent separation.** "The main conversation's auto memory isn't loaded into subagents." "Subagents can also maintain their own auto memory" via the subagent `memory` field. (`#claude-md-vs-auto-memory`, `#how-it-works`)
- **Inspect/edit/delete.** "Auto memory files are plain markdown you can edit or delete at any time." The `/memory` command lists memory locations, toggles auto memory, and opens files in your editor; "when you ask Claude to remember something … Claude saves it to auto memory. To add instructions to CLAUDE.md instead, ask Claude directly." (`#audit-and-edit-your-memory`, `#view-and-edit-with-memory`)
- **Retention.** Memory files are excluded from the session-transcript cleanup sweep ("`cleanupPeriodDays`"), so "`MEMORY.md` and topic files stay until you or Claude edits or deletes them." (`#storage-location`)

Related first-party API surface: the Anthropic **Memory tool** (`memory_20250818`) is a client-side file store at `/memories` with `view/create/str_replace/insert/delete/rename` commands; the injected system instruction is "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE … record status / progress / thoughts in your memory … context window might be reset at any moment." Storage is implemented by your app, not by Anthropic. (<https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool>, `#prompting-guidance`)

## 2. OpenAI Codex — Memories vs AGENTS.md

First-party docs: <https://developers.openai.com/codex/customization/memories>; <https://developers.openai.com/codex/agent-configuration/agents-md>

- **The cardinal split (checked-in rule vs recall).** "Keep required team guidance in `AGENTS.md` or checked-in documentation. Treat memories as a helpful recall layer, not as the only source for rules that must always apply." (`memories`, top)
- **AGENTS.md is the canonical, committed layer.** "Codex reads `AGENTS.md` files before doing any work." Discovery builds an instruction chain: global (`~/.codex/AGENTS.md` or `AGENTS.override.md`) then project (root → cwd, one file per directory, `AGENTS.override.md` → `AGENTS.md` → fallback names), concatenated root-down so nearer files "override earlier guidance because they appear later in the combined prompt"; loading "stops … once the combined size reaches … `project_doc_max_bytes` (32 KiB by default)." (`agents-md`, `#how-codex-discovers-guidance`)
- **Memories are a separate local store, off by default.** "Local Codex memories are off by default"; enable in Settings → Personalization or with `[features] memories = true`. (`memories`, `#configure-local-memories`)
- **Automatic capture from prior chats, gated on idleness.** "After you enable memories, Codex can turn useful context from eligible prior chats into local memory files. Codex skips active or short-lived sessions, redacts secrets from generated memory fields, and updates memories in the background instead of immediately at the end of every chat. … Codex waits until a chat has been idle long enough to avoid summarizing work that's still in progress." (`memories`, `#how-local-codex-memories-work`)
- **Quota gating.** "Memory generation can also skip a background pass when your Codex rate-limit remaining percentage is below the configured threshold" (`memories.min_rate_limit_remaining_percent`). (`memories`, `#how-local-codex-memories-work`, `#configure-local-memories`)
- **Storage.** "Codex stores memories under your Codex home directory … `~/.codex`. The main memory files live under `~/.codex/memories/` and include summaries, durable entries, recent inputs, and supporting evidence from prior chats. Treat these files as generated state … don't rely on editing them by hand." (`memories`, `#local-memory-storage`)
- **Per-chat controls.** `/memories` chooses whether the current chat "can use existing memories" and "whether Codex can use the chat to generate future memories". (`memories`, `#control-local-memories-per-chat`)
- **Config knobs naming the pipeline.** `memories.generate_memories` (whether new chats become memory-generation inputs); `memories.use_memories` (inject existing memories into future sessions); `memories.disable_on_external_context` (exclude chats that used MCP/web/tool search); `memories.extract_model` and `memories.consolidation_model` (per-chat extraction vs global consolidation). (`memories`, `#configure-local-memories`)
- **No user-approval gate; review is after the fact.** Docs instruct "you should still review memory files before sharing your Codex home directory or generated memory artifacts" — capture is automatic, with secret redaction, not approval-gated. (`memories`, `#how-local-codex-memories-work`, `#review-local-memories`)
- **Decay is not documented first-party.** The memories page documents consolidation (`consolidation_model`) and per-chat opt-out, but no time-based decay/expiry of memories. (Absence noted against `#configure-local-memories`.)

## 3. Aider — conventions file

First-party doc: <https://aider.chat/docs/usage/conventions.html>

- **The mechanism is a manually-written, manually-loaded conventions file.** "The easiest way … is to simply create a small markdown file and include it in the chat … create a file like `CONVENTIONS.md` … and add it to the aider chat." (`#specifying-coding-conventions`)
- **Loaded read-only and cached.** "It's best to load the conventions file with `/read CONVENTIONS.md` or `aider --read CONVENTIONS.md`. This way it is marked as read-only, and cached if prompt caching is enabled." (`#specifying-coding-conventions`)
- **Can be auto-loaded via config.** "configure aider to always load your conventions file in the `.aider.conf.yml` config file: `read: CONVENTIONS.md`." (`#always-load-conventions`)
- **No auto-capture or learning.** Aider has no first-party automatic "learned lessons" memory: conventions are authored by the human and read/write only via the normal chat file tools. There is no documented capture, de-duplication, or recall layer beyond the file contents being in the chat context. (Source is the conventions page itself; no such feature is described there.)

## 4. Letta / MemGPT — the self-editing memory architecture

Paper (primary): Packer et al., "MemGPT: Towards LLMs as Operating Systems," arXiv:2310.08560v2, <https://arxiv.org/html/2310.08560v2>. Product docs: <https://docs.letta.com/agent-sdk/memory/>.

- **Core idea — the model pages its own context.** "We treat context windows as a constrained memory resource … allow the LLM to manage what is placed in its own context … retrieve relevant historical data missing from what is placed in-context, and also evict less relevant data from context and into external storage." (`§1 Introduction`)
- **Two tiers with OS names.** "Main context (analogous to main memory/RAM) and external context (analogous to disk memory)." Main context = the prompt tokens; external context = everything outside the window, "always explicitly moved into main context" to be seen. (`§2`)
- **Main context has three contiguous sections.** "System instructions (read-only … control flow, usage of the different memory levels, how to use the MemGPT functions); working context (a fixed-size read/write block of unstructured text, writeable only via MemGPT function calls … key facts, preferences, and other important information about the user and the persona); FIFO queue (rolling history of messages …). The first index in the FIFO queue stores a system message containing a recursive summary of messages that have been evicted from the queue." (`§2.1`)
- **STORE is triggered by memory pressure, not by the user.** "When the prompt tokens exceed the 'warning token count' … (e.g. 70% of the context window), the queue manager inserts a system message … warning the LLM of an impending queue eviction … to allow the LLM to use MemGPT functions to store important information … to working context or archival storage." At "flush token count" (100%), "the queue manager flushes the queue … evicts … 50% of the context window, generates a new recursive summary using the existing recursive summary and evicted messages … the evicted messages … are stored indefinitely in recall storage and readable via MemGPT function calls." (`§2.2`)
- **RECALL is self-directed via function calls.** "Memory edits and retrieval are entirely self-directed: MemGPT autonomously updates and searches through its own memory based on the current context." Implemented by "explicit instructions within the system instructions" — a description of the memory hierarchy plus "a function schema (complete with their natural language descriptions) that the system can call." (`§2.3`)
- **Two external stores.** The paper's architecture distinguishes "recall storage (the MemGPT message database)" for the raw message log (`§2.2`) and "archival storage (a read/write database storing arbitrary length text objects)" (`§2.2`, `§2.3`); Figure 3 labels external context as "the archival and recall storage databases." In the product line these became **core memory** and **archival memory** — "core memory" appears in the paper itself: the DMR instructions say to answer "using the information in core memory and conversation_search" (`Appendix 6.1.1`), and Archival storage supports embedding search ("uses PostgreSQL … with vector search enabled via the pgvector extension," `§3.2.1`).
- **The store-vs-recall decision loop.** The feedback loop of warnings → store, and function calls → search/paginate, is the STORE-vs-RECALL mechanism: "This feedback loop enables the system to learn from its actions … MemGPT prompts the processor with warnings regarding token limitations to guide its memory management decisions. Additionally, our memory retrieval mechanisms … implement pagination to prevent retrieval calls from overflowing the context window." (`§2.3`)
- **Product evolution — memory blocks.** In current Letta, "Memory (organized into blocks) are pieces of context (strings) that are editable by agents via memory tools … memory blocks that are attached to an agent are in-context (pinned to the system prompt). Memory blocks can be attached to multiple agents at once ('shared blocks')." (`docs.letta.com/v1-sdk/concepts/stateful-agents/`, `#memory`) "Important 'core' memories are injected into the context window of the LLM, and the agent can modify its own memories through tools." (`#introduction-to-stateful-agents`)
- **Persisted behind the window.** "All messages are stored, so even after a compaction / eviction, an agent's old messages are still retrievable." (`#messages`)
- **Product evolution — git-backed MemFS + dreaming.** An agent's memory "lives in a git repository owned by the agent, which MemFS projects onto whatever computer the agent is working on. Edits become memory once they are committed and pushed." Files under `system/` "are in the system prompt every turn. Everything else stays out of context — the agent sees the file tree and reads what it needs." (`docs.letta.com/agent-sdk/memory/`, `#memfs`) **Dreaming** "uses background subagents to review recent conversations, consolidate useful lessons, and update memory without interrupting your active work," triggered by step count or context compaction (`docs.letta.com/configuration/memory`, `#dreaming`); `memory` entries carry `label`+`value` (`docs.letta.com/agent-sdk/memory/`, `#setting-memory-at-creation`).
- **Human teaching path.** `/remember always use pnpm in this repo` — "The agent decides where the lesson belongs and commits the update to MemFS"; `/init` bootstraps/refreshes memory; `/doctor` "audits placement, duplication, and system-prompt token usage." (`docs.letta.com/configuration/memory`, `#teach-your-agent`, `#initialize-memory`)
- **Terminology gap.** Neither the paper nor the current Letta docs use a "memory-ledger" term; the closest published artifacts are the recall-storage message database and the queue's rolling recursive-summary slot (paper `§2.1–2.2`). See "could not source" below.

## 5. zeroshot — Active Memory (the-open-engine/zeroshot)

Primary: `docs/guides/active-memory.md` at blob `7660eea7bf90bfd544d91e948fdd3a1fb9b2f46a` (branch `main`), latest commit touching the path `a80650024d13250c4d1d209629a904a89eb6cf28` (2026-10-24). Rendered copy: <https://zeroshot.sh/docs/current/guides/active-memory/>.

- **What it stores.** "Active Memory preserves concise lessons about costly mistakes and non-obvious work likely to recur." Local SQLite store at `~/.local/state/zeroshot/active-memory/lessons.sqlite3` (or `$XDG_STATE_HOME`, or `$ZEROSHOT_STATE_DIR`), "one database across repositories, outside repository checkouts." (`#active-memory`, `#persistence-and-run-completion`)
- **"Workers never write lessons" — capture is separated from work.** "Workers do not write lessons. After the main graph settles, the built-in postmortem runs inside the same run, using an existing node's model, provider and connections." It has four specialists, two scopes that are strictly isolated: **graph maintenance** (reconcile supplied graph lessons against authored node instructions/output contract), **repository maintenance** (reconcile supplied repository lessons against current authoritative files), **graph discovery** (propose procedural guidance for nodes that executed), **repository discovery** (propose lessons about recurring work). "Neither maintenance specialist receives or can modify lessons from the other scope." (`#active-memory`)
- **Admission gates (capture trigger).** "A lesson needs evidence of expensive failure or substantial exploration, a concrete recommendation and a reason to expect reuse. Task summaries, generic advice and facts obvious from nearby code do not qualify." "Two timeout/crash completions or two provably rejected review-loop visits can qualify. Repository discovery also accepts exploration with at least three distinct tool callbacks spanning five minutes. A single ordinary response-format correction does not qualify." Enforced length limits: "Titles have at most 96 UTF-8 bytes; recommendations have at most 640." (`#active-memory`)
- **Two-tier form.** "The store keeps evidence pointers and provenance separately from the injected card" — the short, injected "card" is separated from the supporting evidence. (`#active-memory`)
- **Reconciliation = learn-once + de-dup.** "Each maintenance specialist keeps, adapts, retires or defers every lesson in its scope. … Maintenance also consolidates overlapping advice … It keeps or adapts one canonical card and retires redundant paraphrases." "The host binds that ID to its frozen supplied revision and owns revision increments; agents do not manage version counters." Each batch "requires exactly one decision per supplied ID." (`#active-memory`)
- **Concurrency-safe, add-only-host.** "The host owns the database outside the checkout and publishes all shared-store mutations. Workers receive a run-scoped retrieval capability. Reconciliation uses expected revisions, atomic transactions and deletion tombstones, so concurrent runs cannot silently overwrite a newer lesson or recreate a retired record from a stale snapshot. Newly published lessons become available to future runs." "Previous contents are not archived, and there is no built-in undo; deletion tombstones retain IDs and revisions rather than card contents." (`#persistence-and-run-completion`)
- **Retrieval is deterministic, not semantic.** "A run freezes an immutable, scoped snapshot. Matching uses resident inverted indexes and performs no model calls … Repository lessons can independently associate with multiple literal files, folders, identifiers or groups of keywords." Scoring: exact root-relative file 1000, containing folder 800, exact whole identifier 700, all terms in an indexed keyword group 500. "Retrieval sorts by descending score … and returns complete cards within the remaining budget. … An ID/revision is supplied once per provider session." (`#indexing-and-retrieval`)
- **Delivery is via harness hooks, right before tool use.** "Codex and Claude use `PreToolUse` additional context through a small native callback helper. … Context guides subsequent model decisions. It cannot revise a tool call already issued, so reads and searches provide the most useful early triggers." "Hook receipts record returned context, not proof that the model followed it." (`#indexing-and-retrieval`)
- **Scope keying.** Graph lessons are keyed to "the authored compiled graph hash plus node ID, optionally repository … Authored graph changes create a new scope; this version does not transfer guidance across graph versions." Repository lessons are scoped per repository. (`#indexing-and-retrieval`)
- **Budget.** `activeMemory.budgetBytes` is "a cumulative context budget per provider session, including card framing. It must be 1 through 16384; cards that do not fit remain undelivered." Postmortem shared wall-clock budget `timeoutMs` 1–600000. (`#configuration`)
- **The documented failure ("workers never write lessons" postmortem).** The commit that fixed evidence loss is `60d1d23e6dae1c8e809bad4049fff3f5c144ac19` ("fix(memory): retain postmortem evidence and reconcile stable lessons (#1290)", 2026-10-24): "Active Memory could lose the worker's costly exploration when a long run filled its evidence budget with the last reviewer's transcript. Postmortems now read bounded history pages and retain evidence fairly across executions … Maintenance now removes unstable source locations and lets the host bind each decision to the supplied lesson revision. This prevents stale line-number guidance and model-generated revision errors." The guide's corresponding rule: "Postmortem history is read in bounded pages; its fixed transcript budget reclaims old records from the execution consuming the most space, so a verbose late reviewer cannot displace all worker evidence." (`#active-memory`)
- **Backfill.** `zeroshot memory init` re-derives lessons from historical local runs via discovery subagents + fresh maintenance specialists, publishing across repositories in one transaction. (`#initialize-from-local-history`)

## 6. Agent-framework memory modules (first-party docs)

### 6a. LangChain / LangGraph

Docs: <https://docs.langchain.com/oss/python/langgraph/memory.md>; <https://docs.langchain.com/oss/python/langchain/short-term-memory.md>

- **Two scopes.** Short-term = thread-scoped, "persisted to a database using a checkpointer so the thread can be resumed at any time"; long-term = "stored across … threads, recalled at any time … in any thread," "Memories are scoped to any custom namespace." (`memory.md`, `#memory-overview`)
- **States are JSON documents under namespace + key.** "LangGraph stores long-term memories as JSON documents in a store … organized under a custom `namespace` (like a folder) and a distinct `key` (like a file name)"; the `Store` "supports both semantic search and filtering by content." (`memory.md`, `#memory-storage`, `#collection`)
- **Memory taxonomy (semantic / episodic / procedural).** Semantic = facts ("a single, continuously updated 'profile' … or a collection of documents"); episodic = experiences ("often implemented through few-shot example prompting"); procedural = rules/instructions ("a combination of model weights, agent code, and agent's prompt … it is more common for agents to modify their own prompts," via "Reflection" / meta-prompting). (`memory.md`, `#semantic-memory`, `#episodic-memory`, `#procedural-memory`)
- **Write timing — hot path vs background.** "In the hot path" (tool called during the run; e.g. ChatGPT's `save_memories`) vs "in the background" (separate task/cron/manual; "eliminates latency … separates application logic from memory management"). (`memory.md`, `#writing-memories`)
- **Eviction is developer-authored.** Short-term history managed by "Trim messages / Delete messages (`RemoveMessage`) / Summarize messages" patterns, with a built-in `SummarizationMiddleware(trigger=("tokens", 4000), keep=("messages", 20))`. (`short-term-memory.md`, `#common-patterns`, `#summarize-messages`)

### 6b. LlamaIndex

Doc: <https://developers.llamaindex.ai/python/framework/module_guides/deploying/agents/memory/>

- **Buffer + blocks.** "the `Memory` class [has] both short-term memory (i.e. a FIFO queue of messages) and optionally long-term memory (i.e. extracting information over time)." The agent "makes calls to `memory.put()` to store information, and `memory.get()` to retrieve." (`#concept`)
- **Deprecated names are the classic abstractions.** `ChatMemoryBuffer` (last X messages within a token limit), `ChatSummaryMemoryBuffer` (buffers + periodic summarization), `VectorMemory` (vector-DB retrieval of similar messages), `SimpleComposableMemory` (composes several). (`#deprecated-memory-types`)
- **Long-term form — memory blocks with priorities.** `StaticMemoryBlock` (always injected), `FactExtractionMemoryBlock` (LLM extracts facts, `max_facts=50`, auto-summarized when overfull), `VectorMemoryBlock` (batches of flushed messages in a vector store). (`#long-term-memory`)
- **Token-budget eviction with flush + truncation.** `token_limit` (default 30000); when short-term history exceeds `chat_history_token_ratio` (0.7) the oldest `token_flush_size` (3000) messages are flushed to long-term blocks; if total exceeds `token_limit`, blocks are truncated by `priority` ("`priority=0` … always kept"). (`#short-term-memory`, `#long-term-memory`)
- **Backing store is a DB.** "By default, the `Memory` class is using an in-memory SQLite database. You can plug in any remote database" or a custom `AsyncDBChatStore`. (`#remote-memory`, `#custom-chat-store`)

### 6c. CrewAI

Doc: <https://docs.crewai.com/en/concepts/memory>

- **Unified memory class.** "a single `Memory` class that replaces separate short-term, long-term, entity, and external memory types"; "Memory uses an LLM to analyze content when saving (inferring scope, categories, and importance) and supports adaptive-depth recall with composite scoring." (`#overview`)
- **Hierarchical scopes.** "Memories are organized into a hierarchical tree of scopes, similar to a filesystem" (`/`, `/project/alpha`, `/agent/researcher`); recall within a scope searches only that branch; `MemoryScope` / `MemorySlice` give subtree or multi-branch views, read-only or not. (`#hierarchical-scopes`, `#memory-slices`)
- **Capture on task completion.** "After each task, the crew automatically extracts discrete facts from the task output and stores them. Before each task, the agent recalls relevant context from memory and injects it into the task prompt." (`#with-crews`)
- **Ranked retrieval.** "composite = semantic_weight * similarity + recency_weight * decay + importance_weight * importance," with exponential recency decay `0.5^(age_days / half_life_days)` (`recency_half_life_days` default 30). (`#composite-scoring`, `#configuration-reference`)
- **Explicit de-dup / learn-once.** "consolidation" on save (similarity above `consolidation_threshold`, 0.85) — the LLM decides `keep / update / delete / insert_new` per existing record; plus "Intra-batch Dedup" dropping near-duplicates ≥ `batch_dedup_threshold` (0.98) within a batch. (`#memory-consolidation`, `#intra-batch-dedup`)
- **Storage / eviction.** LanceDB under `./.crewai/memory` by default; explicit `memory.forget(scope=…)` and `memory.reset()` are the eviction surface; no automatic time-based purge is documented beyond the recency weight's effect on ranking. (`#storage-backend`, `#discovery`, `#configuration-reference`)

| **De-dup / learn-once** | Skips what code derives and what CLAUDE.md already says | None documented (consolidation model only) | None | Self-editing: agent rewrites its own blocks; dreaming consolidation | Maintenance consolidates overlapping cards into one canonical card; one decision per ID/revision | Collection update/delete over existing docs (Trustcall); reflection rewrites the prompt | Fact block `max_facts` summarizes overfull | Consolidation (keep/update/delete/insert_new) + intra-batch dedup |  |
| **Human review** | Always editable/auditable plain markdown (`/memory`) | Review-after-the-fact; per-chat opt-in/out; secret redaction | Full authorial control | `/remember` teaching; `/doctor` audit; agent edits are agent-owned | No interactive gate; host owns store, revisions, tombstones | Developer defines the memory logic end-to-end | Developer configures blocks | Developer-configured; records carry `source`/`private` tags |  |

**What is common across all of them.** Every mature system separates *durable knowledge* from *working context* and, crucially, separates the **canonical, human-authored/reviewed layer** from the **automatic recall layer**: Claude Code's CLAUDE.md vs auto memory, Codex's AGENTS.md vs memories, Letta's developer-set blocks vs agent-edited memory, zeroshot's authored graph/node instructions vs postmortem-produced lesson cards — and the recall layer is always treated as a *helpful addition, not a source of truth*, which is exactly the reconciliation our hazards tracker needs (lessons must never override or duplicate the committed record; they only shorten the path back to it). The capture trigger is consistently *not* the worker at task time: Claude and Codex gate on idleness/background passes, Letta gates on memory pressure or scheduled "dreaming," and zeroshot makes it a deliberate rule — workers never write lessons; a postmortem/maintenance pass does. Learn-once is achieved not by preventing duplicates at write time alone but by a *reconciliation/maintenance pass* that keeps, adapts, retires, or merges each lesson against current authoritative files (zeroshot's "one canonical card," CrewAI's consolidation, Letta's `/doctor` and dreaming). Retrieval is dominated by two options — *whole-store-injection under a hard byte/line budget* (Claude's 200-lines/25KB index, zeroshot's `budgetBytes`, LlamaIndex's token limit) and *on-demand lookup* (keyword/identifier/vector search, pre-tool-use hooks) — and every system keeps evidence/precision separate from the terse injected card or index so the always-loaded surface stays tiny while detail stays recoverable. Finally, eviction is everywhere *budgeted and irreversible-but-tombstoned* (summarize/flush, truncate by priority, forget) rather than unbounded growth, and the storage is consistently machine- or host-local and keyed per-project/repository/graph so lessons don't leak across scopes.
